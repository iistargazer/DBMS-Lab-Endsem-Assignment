# DBMS Lab — End Semester Analysis

Analysis of 120 days of player telemetry (2026-01-01 to 2026-04-30) for a live-service
mobile game: 80,295 players, 667,435 active player-days, five tables, $214k of net in-app
revenue.

**Rohan Chinta — 24MAB0A27**

Everything in `outputs/tables/` is generated from the queries in `sql/` and the
modelling scripts in `code/`, and the deck is rendered from those CSVs; nothing is
typed in by hand. `make all` rebuilds the lot — tables, models, charts and slides.

---

## Quick start

```bash
make all            # or: python run.py all
```

That builds the warehouse from the committed parquet snapshots, re-runs every query
(one CSV per result block to `outputs/tables/`), refits both models and renders
`deck/DBMS_EndSem_Deck.pptx` from the resulting CSVs. It takes about 35 seconds from a
clean tree.

Targets:

| Command | What it does |
|---|---|
| `make all` | warehouse + queries + models + deck (default) |
| `make extract` | re-derive `player_profile.csv` / `purchase.csv` from the PDFs |
| `make tables` | re-run queries only |
| `make models` | re-run the bootstrap intervals and the churn model |
| `make ltv` | re-run the optional 90-day value model |
| `make deck` | rebuild the deck from the CSVs only (no warehouse needed) |
| `make everything` | extract + warehouse + queries + models + deck |
| `make clean` | remove generated tables, charts, the deck and the database |

On Windows the interpreter can be overridden: `make PYTHON=py all`. Without GNU make,
`python run.py <target>` runs the identical steps.

Requirements: Python 3.10+, `duckdb`, `pandas` (installed by `make setup`). Only
`make extract` needs poppler's `pdftotext`.

A query file is a sequence of named blocks:

```sql
-- name: daily_health_by_platform
SELECT ... ;
```

`02_run_sql.py` executes each block separately and writes
`outputs/tables/<file>__<block>.csv`, so every number in the write-up can be traced
back to a named query and a committed output file.

## The deck

`code/06_build_deck.py` renders `deck/DBMS_EndSem_Deck.pptx` — 8 readout slides and 11
appendix slides — with `python-pptx` and `matplotlib`. Every number on every slide is
read from `outputs/tables/*.csv` at build time and the script stops if a file it needs
is missing, so the deck cannot drift from the analysis. The five charts are written to
`outputs/figures/` as PNG and embedded; `make deck` rebuilds the slides alone, in a
couple of seconds, without touching the warehouse.

## Data

Five tables. Three arrived as CSV; **`player_profile` and `purchase` arrived as PDF
printouts** (3,492 and 672 pages) with the columns split across alternating pages.

`code/00_extract_pdf_tables.py` decodes that structure — main columns on one page,
trailing columns on the next, paired positionally — and refuses to write a table
unless every paired page yields the same row count on both sides. It recovers
80,295 players and 15,426 purchases with zero pairing failures, and cross-checks
clean: every buyer exists in the profile, `first_purchase_date` is non-null for
exactly the 11,054 players with transactions, and there is no activity dated before
a player's install date.

The three source CSVs are ~100 MB together, so the raw files are gitignored and the
typed parquet snapshots (22 MB) are committed instead. Put the original files in
`data/raw/` and run `make extract data` to rebuild from source.

## What is in the analysis

**1(a) Daily health** — `q1a`: DAU, gross and net revenue, ARPDAU and purchase rate
by day and platform. Purchase rate uses purchasers who were *also active that day*,
because 41% of sale-day transactions belong to players with no session row that date
(see `dq16`).

**1(b) Retention cohorts** — `q1b`: weekly install cohorts × day 1/7/14/30. Two
boundary rules: cohorts before 2026-01-01 are excluded (their day-N activity predates
the extract), and a cell is left blank unless every player in the cohort has had a
full N days of observation. No zeros are substituted for unobserved days.

**1(c) Spender behaviour** — `q1c`: revenue concentration ranked both among payers
only and among all players (top 1% = 9.1% vs 40.2% of revenue respectively), time to
first purchase restricted to players with ≥30 days of follow-up, and repeat purchase
gaps via `LAG` rather than a self-join.

**1(d) Rewarded ads** — `q1d`: cap saturation split by cap value, daily volumes, and
the two days with no ad events at all.

**2(a) Why is ARPDAU falling** — `q2a`: a shift-share decomposition of the 16.7% fall
between the first and last 30 days of the window into within-tier, mix and interaction
terms, run on net revenue, with a mean-of-daily-ratios variant as a weighting check
and an install-mix drift table to show the mix term is a real change in acquisition
rather than a coding artefact. `v_day_tier_facts` (in `sql/00_views.sql`) is the view
behind it.

**2(b) Are the sales making money** — `q2b`: twelve tests of the pull-forward claim,
including a per-window counterfactual built from mid-cycle days, a pre/post trough
decomposition, and the same decomposition for first-time payers.

**3. Is one acquisition channel buying better players?** — `q3`: every install from
2026-01-01 to 2026-03-31 (37,489 of them) measured over the same D0–D30 window from
its own install date, so no channel benefits from having arrived earlier, and no April
install is judged on a month it has not had. Each metric is then computed inside the
8 platform × country-tier cells and re-weighted to the cohort's overall mix, because
paid_video delivers 65% tier-4 traffic against organic's 18% and tier is the strongest
correlate of value in the data. `code/03_channel_ci.py` resamples players within cells
to put intervals on both the standardised rates and the channel-to-channel differences.

**4. Who is about to churn?** — `q4` and `code/04_churn_model.py`: a weekly panel of
player-snapshots (9 snapshots, 175,644 rows) labelled "no activity in the following 14
days" for players active in the previous 7. Logistic regression on frequency, depth,
tenure and money, trained on snapshots to 2026-03-23 and tested out-of-time on 44,141
players, with calibration, a threshold table and a cost curve.

**4(b) What is a new install worth over 90 days?** — `q4b` and `code/05_ltv_model.py`:
restricted to the 9,809 installs that have 90 observed days, and to features known by
the end of day 7. The target is 77.8% zeros, so a one-part regression is reported
only to be rejected: a two-part model (odds of paying × expected spend given payment)
is fitted instead, and both are ranked against the free day-7-spend heuristic. The rank
transfer check between the January and February cohorts is in `q4b_ltv__ranking_comparison`;
the script asserts that the cohort definition matches the `v_ltv_cohort` view.

## Headline findings

**ARPDAU fell 16.7% and nothing about the game got worse.** ARPDAU over the first 30
days of the window is $0.3488; over the last 30 it is $0.2906. Decomposed: if only the
per-tier rates had moved, ARPDAU would have *risen* 7.3% (+$0.0255); letting only the
tier mix move takes 21.5% away (−$0.0751); the interaction takes the last $0.0085.
April's rates applied to January's mix give $0.3743, and every tier improved — +5.4%,
+10.4%, +11.7%, +0.8%. What changed is who is playing: tier 4 goes from 17.7% of DAU
to 46.0%, paid_video from 15.1% of installs to 69.2%, and tier-4 installs from 18.1%
to 62.7%. The mean-of-daily-ratios version of the same measure falls 17.6% (0.3506 →
0.2889), so the direction is not an artefact of the weighting.

**Sales are mostly timing, not incremental.** Promotion days earn $5,307/day against
$1,244 on ordinary days, with the same DAU, the same revenue per buyer ($14.62 vs
$14.16) and the same basket size. But the four days before each window run at 0.40–0.48
of mid-cycle revenue and the three days after at 0.60–0.74. Net of that trough, the
eight windows add about **$13,083** on $84,920 of sale-day revenue — roughly 85% of the
spike is money moved, not money created.

**The promotions carry no price incentive.** `usd_amount` and `currency_granted` are
identical on sale and non-sale transactions for all six packs (`dq09`). Whatever the
promotion does, it is not a discount in the transaction record.

**The ad cap is not binding.** 1.3% of cap-5 player-days and 0.02% of cap-8 player-days
reach the cap; players average 1.35 completed ads per ad-watching day, and 44% of DAU
never watch one.

**The acquisition channels differ in who they buy, not in what those players are
worth.** Raw, paid_video looks like a bad channel: $1.60 revenue per install against
organic's $2.46, and 9.2% converting to a payer against 13.5%. But 65% of its installs
are tier 4 against 18% for organic. Standardised to a common platform/tier mix the gap
disappears — $2.12 against $2.15, conversion 11.7% against 12.2%, day-30 retention
13.8% against 13.7% — and the bootstrap intervals on the differences all cross zero
(paid_video minus organic revenue per install: −$0.02, 95% CI −$0.34 to +$0.33).
Paid_video's payers actually spend slightly *more* each ($17.41 vs $16.85 standardised).
The one real difference is ads: 5.28 completed ads per install against organic's 5.80.

**Churn is driven by depth, not by how you were acquired.** The model separates churners
from non-churners out of time at AUC 0.741 (95% CI 0.735–0.747), and 0.702 on the 16,503
test players it has never seen. More sessions and more playtime per active day both
lower the odds (OR 0.78 and 0.80 per SD), as does completing rewarded ads (0.84);
longer tenure raises them (1.71). Channel barely matters once tier and behaviour are in
the model (paid_video OR 0.96, paid_social 1.07) — the raw gap (11.7% churn for
paid_video against 15.3% for organic) is the same tier confound as above. A score of
0.30 or more flags 16% of players, catches 37% of churners and is right 34% of the
time — 2.3× the base rate. The threshold that maximises expected value under the
stated economics (a $0.50 contact that saves a quarter of a $12 player) is lower,
0.15: 37% of players contacted, 27% precision, about $117 per 1,000 players, against
−$55 for contacting everyone.

**The 90-day value model is a ranker, not a bid rule.** Only 9,809 installs (12.2%)
have 90 observed days, 77.8% of them are worth nothing and the mean is $4.63. The
two-part model beats a one-part regression on every ranking metric, and the top decile
it picks holds 46.3% of the cohort's 90-day revenue against 43.7% for the free
day-7-spend heuristic. On global Spearman the heuristic wins (0.47 vs 0.35), because
it puts every non-payer in one tie block; the model wins where the money is, at the
top. Ranks transfer between cohorts (0.34 in January, 0.34 in February) but levels do
not: the labelled cohort is 15.1% paid_video against April's 69.2%, so those dollars
describe the old mix rather than the current one.

**Data-quality issues handled** (full register in `sql/q0_data_quality.sql`):
`ad_view` timestamps are logged on a clock 8 hours ahead of every other table, pushing
7,732 rows onto 2026-05-01; 228 refund rows; 122 duplicate `purchase_id`s; `sale_flag`
also fires on refund rows, which inflates a naive sale-day count from 16 to 58; 110
players with purchases dated before their install date; purchases left-truncated at
2026-01-01, so time-to-first-purchase must exclude pre-window installs; a `currency_spend`
GRIND row at 75.8M against a p99.9 of 3,229; two days with zero ad events (5–6 March)
while DAU held; and the brief's claim that `country_tier` is null for non-purchasers,
which is never true in the data.

## Limitations

- No marketing cost, so acquisition channels cannot be compared on return — only on
  player quality. A channel that is cheap enough can still be the right buy.
- The churn model is a ranker, not a causal model: the coefficients are conditional
  associations, and no experiment backs them. Its cost curve also rests on inputs the
  data does not contain (contact cost, save rate), so those are assumptions stated in
  `code/04_churn_model.py`, not measurements.
- Out-of-time is not fully out-of-player: 16,503 of the 44,141 test players never appear
  in training, and the AUC on those (0.702) is the leak-free number to quote.
- No holdout: every 15-day cycle contains a sale, so the counterfactual is
  reconstructed from neighbouring days rather than observed. A skipped window or a
  geo holdout would settle it properly.
- Purchase data starts 2026-01-01, so pre-window players cannot be used for
  time-to-first-purchase or early-retention measures. This is also what caps 4(b) at
  12.2% of installs.
- 4(b) is fitted on a cohort that is 15.1% paid_video against 69.2% in April. The
  ranking transfers; the dollar levels do not, so they describe the labelled cohort
  rather than a forecast for today's installs.
- The one-part 90-day regression is reported only to show that it ranks worse than a
  free heuristic. With 77.8% zeros it spends its capacity separating payers from
  non-payers and orders the paying tail poorly; it is not a candidate model.
